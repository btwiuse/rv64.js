# WANIX rv64.js backend

This integration mirrors WANIX's `v86/` driver layout without modifying the
WANIX source tree. `make bundle` produces
`rv64.tgz`, containing `rv64-vm.wasm` (the WANIX adapter) and
the sibling `rv64.js` and `rv64_wasm.wasm` runtime files. Bind the archive at
`#vm/rv64` and start it with `<wanix-vm type="rv64">`. The adapter resolves
the runtime beside its own executable, so independently named RV64 variants
can coexist in one WANIX namespace.

The adapter boots `boot/Image` directly and mounts the current WANIX namespace
as the guest's `host9p` root. Mirroring the copy/v86 device layout, the
interactive terminal runs on the `hvc0` virtio console (resizable: the
term's `winch` signal is forwarded to `RV64.resize`, so `stty size` and
SIGWINCH follow the panel), and the 8250 UART `ttyS0` carries the WANIX
host-export stream.

From the rv64.js checkout, build the runtime archive and both architecture-
matched Linux namespace archives with:

```sh
make -C integrations/wanix bundle linux
```

The normal `rv64.tgz` bundle uses the immutable official
[`v0.3.0` release](https://github.com/btwiuse/rv64.js/releases/tag/v0.3.0).
The Makefile verifies the published `rv64.js` and `rv64_wasm.wasm` SHA-256
values before packaging them with the locally built WANIX adapter. This keeps
ordinary WANIX installations on a named release instead of silently depending
on the checkout's current Rust and JavaScript sources.

For emulator development, build `dist/rv64-workspace.tgz` from the current
checkout instead:

```sh
make -C integrations/wanix bundle-workspace
```

`linux` produces `wanix-linux-rv64.tgz` and `wanix-linux-x86.tgz`. Both are
generated by the same script from Alpine 3.22, install the same package set
(including Python), use Linux 6.12.7 from this flake, copy the same guest init,
and build WANIX helpers from the same pinned source revision. The unavoidable
differences are the guest binaries and kernel device paths: RV64 uses a raw
RISC-V `Image` with virtio-mmio, while copy/v86 uses an i686 `bzImage` with
virtio-pci. copy/v86 does not implement x86-64 long mode.

For the three-way comparison, `make comparison` additionally produces:

- `dist/rv64-legacy.tgz`, containing the loader and emulator from the immutable
  GitHub `v0.1.0` release (the pre-rewrite JIT). The build verifies the pinned
  SHA-256 values before packaging either download.
- `dist/rv64-jit.tgz`, containing the loader and emulator built from the current
  workspace (the JIT rewrite).

The small WANIX adapter is shared, but each archive has the executable name
required by its WANIX type (`rv64-legacy-vm.wasm` or `rv64-jit-vm.wasm`).
The legacy inputs come directly from the official
[`v0.1.0` release](https://github.com/ibuildthecloud/rv64.js/releases/tag/v0.1.0)
(tag commit `aea8b8234a4ba3bae146837b114284c52604fb5d`) and are pinned as:

- `rv64.js`: `54df79c8b35cf50bcee34c4af02d7eb02b09e0439b717ee75bb830e733595b12`
- `rv64_wasm.wasm`: `001e5158b8f47f981371eae201079e6ec3eb632ab39ba1d0caf9a1ca5412b049`

`build-linux-bundle.sh` checks out the pinned WANIX revision in a temporary
directory and cross-compiles its `wexec` and `hostexport` guest utilities for
the selected architecture. Set `WANIX_GUEST_ARCH=riscv64` or
`WANIX_GUEST_ARCH=x86`; the Makefile targets do this automatically. The small
RISC-V-only build patch teaches WANIX's platform-stat helper about Go's
`linux/riscv64` `Stat_t`; it does not require a WANIX checkout to be modified
or committed.

The adapter enables rv64.js's browser `fetch` network backend. It uses the
hosted Cloudflare Worker at
`wss://rv64-http-relay.darren-e4d.workers.dev/relay` as the default CORS
fallback; set `RV64_RELAY_URL` in the WANIX VM environment to override it.
The guest is configured as `10.0.2.15`, uses `10.0.2.2:8080` as its HTTP(S)
proxy, and installs the per-VM proxy CA from the `rv64-proxy` 9P export so
HTTPS clients such as `apk` can use the fetch backend.

Serve the two files from `dist/` and bind them from otherwise stock WANIX:

```html
<wanix-bind dst="." type="archive" src="/assets/wanix-linux-rv64.tgz"></wanix-bind>
<wanix-bind dst="#vm/rv64" type="archive" src="/assets/rv64.tgz?v=0.2.0"></wanix-bind>
<wanix-vm type="rv64" export="ttyS0" mem="1G" term start></wanix-vm>
```

## Why rv64.js 9P needed an adapter

The existing rv64.js 9P implementation and v86's WANIX integration use the
same guest-visible protocol: 9P2000.L over virtio. They originally differed at
the host boundary. rv64.js contained a synchronous Rust 9P server backed by a
tar-loaded `MemFs`; v86 exposes raw request bytes through an asynchronous
`handle9p(request, callback)` hook. WANIX needs the latter because WANIX itself
owns the live namespace and may answer requests asynchronously.

rv64.js now supports both modes. Its original in-process server remains useful
for standalone and native use, while the external backend holds the guest
virtqueue entry pending, forwards the raw request to WANIX, and completes that
entry when WANIX returns the tagged reply.

## Side-by-side WANIX demos

`v86-rv64-side-by-side.html` is the tested two-VM demo. Copy it into WANIX's
`examples/` directory after building the normal v86 assets and the rv64.js
bundles. Both guests bind the same WANIX namespace at `/shared`; the page also
installs `wtop`, `wrepeat`, and a small Python benchmark in that namespace.

`v86-rv64-three-way.html` adds independently started panes for copy/v86,
legacy rv64.js `v0.1.0`, and the workspace JIT rewrite. Build and install its
RV64 inputs with:

```sh
make -C integrations/wanix comparison linux
mkdir -p /path/to/wanix/rv64 /path/to/wanix/extras/dist
cp integrations/wanix/dist/rv64-{legacy,jit}.tgz /path/to/wanix/rv64/
cp integrations/wanix/dist/wanix-linux-{rv64,x86}.tgz /path/to/wanix/extras/dist/
cp integrations/wanix/v86-rv64-three-way.html /path/to/wanix/examples/
```

WANIX's normal `v86/v86.tgz` and `dist/` runtime assets must also be built. The
stock `extras/dist/wanix-linux.tgz` is deliberately not used: it currently has
a different kernel, init, and package set. Open the copied page through WANIX's
HTTP server, then use each pane's **Start** button. A `started` label means the
VM scheduler is running, not that its quiet boot has reached a shell. Starting
all three is useful as a functional demo, but it creates CPU, memory, and
Wasm-tier contention and is not a trustworthy performance run.

The two RV64 panes pass `rv64.benchmark=1`, which skips the optional fetch
proxy/CA setup that the included benchmark does not use. Normal `rv64.tgz`
consumers retain the existing fetch-network behavior.

The rewrite pane uses the in-module interpreter for residual execution together
with the stable loader's async page JIT. Hotness is tracked by
safe virtual-to-physical code-page mapping, and generated region modules are
compiled through `WebAssembly.compile` with at most two builds in flight. On
engines with Wasm tail calls, one shared table-owning trampoline connects hot
generated regions without growing the call stack or making every generated
module import the table. The adapter still accepts the host-only
`rv64.jit=off` flag for explicit interpreter controls; it removes that flag
from the guest command line and disables JIT dispatch before starting the
scheduler.

After `make comparison`, the short non-Linux structural baseline is:

```sh
node tests/interpreter-old-new-baseline.mjs
```

It runs the exact two packaged cores in alternating fresh Node processes,
requires every JIT activity counter to remain zero, and reports all raw paired
samples. Treat it as a direct-driver diagnostic; `/shared/bench.py` remains the
manual guest-workload comparison.

For less misleading manual timings, reload the page, start only one candidate,
wait for its shell, and run `python3 /shared/bench.py` at least twice. Record
the first and repeated results separately, then reload before selecting the
next candidate. Page reload does not guarantee that an engine discarded its
Wasm compilation cache or tiering state; use a fresh browser process and fresh
profile for cold-compilation claims, and alternate candidate order across
runs. Boot-to-shell is a separate cold metric; do not fold it into the repeated
benchmark result.

The controlled comparison is orchestrated by `tests/run-wanix-pairs.mjs`, which
pre-registers and runs alternating fresh-process pairs under one experiment
lock. `tests/wanix-v86-matched-smoke.mjs` executes each leg and
`tests/analyze-wanix-pairs.mjs` validates the immutable artifacts, chronology,
runtime counters, identities, checksums, and paired interval. The exact
five-pair Chrome/Edge commands and current non-inferiority method are recorded
in `docs/jit-rewrite/REPRODUCING.md`.

The demo exercises a few WANIX runtime capabilities that are not present at
the pinned upstream revision. Apply the included patch from the root of a
WANIX checkout before rebuilding WANIX:

```sh
git apply /path/to/rv64.js/integrations/wanix/wanix-host-js.patch
```

`wanix-host-js.patch` makes JavaScript tasks use their task namespace, passes
their environment into the worker, exposes their captured standard output and
error as `/task/<pid>/fd/{1,2}`, and terminates the worker when the task exits.
The matched guest builder installs Python in both architecture roots, so the
older `wanix-x86-python.patch` workaround for WANIX's stock image is no longer
needed by these pages.
