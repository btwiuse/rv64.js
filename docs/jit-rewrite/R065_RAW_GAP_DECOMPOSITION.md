# R065 Raw Versus Emulator-Normalized Gap

## Why this distinction is required

The three-way scorecard deliberately preserves user-visible wall time, but its
copy/v86 and rewrite guests execute different ISAs and compiler outputs. A raw
wall-time loss is therefore the product of two terms:

```text
rewrite time / v86 time
  = (rewrite guest instructions / v86 guest instructions)
  * (rewrite time per guest instruction / v86 time per guest instruction)
```

Both terms matter to the product goal, but only the second is primarily an
emulator/JIT throughput measure. Reporting only their product risks tuning the
JIT against work generated by the guest compiler.

## Accepted R054 Compile decomposition

The authoritative report is
`target/bench/r054-final-three-way-rerun/scorecard-v2-2026-08-08T23-01-30-777Z.json`.
Its three STEADY trials are below; v86's phase stays below 2^32 instructions,
so its architectural counter does not wrap.

| Engine | Times (ms) | Guest instructions | Median throughput |
| --- | --- | --- | ---: |
| rewrite | 1055.025, 1060.937, 1075.401 | 325,692,516; 325,714,756; 325,725,700 | 307.007 MIPS |
| copy/v86 | 718.472, 723.578, 715.389 | 248,968,916; 248,939,086; 248,918,030 | 346.484 MIPS |

Using the medians:

- raw rewrite/v86 time ratio: **1.4767x**;
- RV64/i386 guest-work ratio: **1.3084x**;
- rewrite/v86 time-per-instruction ratio: **1.1286x**;
- rewrite/v86 emulator throughput: **0.8861x**;
- throughput required for raw parity: **453.344 MIPS**, 1.4767x current
  rewrite and 1.3084x v86.

The earlier independent QEMU user-mode count corroborates the cause using only
the native TCC binaries: 290,675,966 RV64 versus 231,421,773 i386 instructions
(1.256x), with similar reads but 20.9% more RV64 writes. The scorecard's larger
1.308x ratio includes kernel/shell work around the same compile.

## Consequence for the goal

Accepted rewrite is not 47.7% behind v86 purely as an emulator. It is 12.9%
behind per guest instruction while being asked to execute 30.8% more guest
instructions. Merely reaching per-instruction parity would predict roughly
941 ms for rewrite Compile, still about 31% slower than v86's 718 ms. Raw
parity requires the emulator to outperform v86 by about 30.8% per guest
instruction, reduce RV64 guest work, or combine both.

This does not relax the raw scorecard verdict. It changes candidate admission:

1. JIT/runtime changes must report both raw time and MIPS; coverage or module
   latency alone is insufficient.
2. A claimed emulator-parity change must close the 12.9% normalized deficit
   without a correctness or browser regression.
3. A claimed raw-parity change must also explain how it overcomes the 30.8%
   guest-work multiplier. Benchmark-specific compiler flags or binaries cannot
   be credited as a JIT optimization.
4. Boot needs its own decomposition because v86 includes an x86 firmware/
   bzImage path while rewrite directly enters the RISC-V kernel. The harness
   now records v86's read-only architectural count outside the timed interval;
   raw wall time remains authoritative.

## Boot decomposition

The balanced three-pair exploratory report is
`target/bench/r065-boot-decomposition/scorecard-v2-2026-08-09T02-16-59-239Z.json`.
It uses exact production R054, the pinned v86 build, the same readiness marker,
fresh processes, CPUs 8-15, and unchanged timing. The added counter read occurs
before and after—not inside—the scored interval.

| Engine | Times (ms) | Guest instructions | Median throughput |
| --- | --- | --- | ---: |
| rewrite | 2238.928, 2291.808, 2289.835 | 180,799,429; 180,815,542; 180,819,086 | 78.964 MIPS |
| copy/v86 | 1514.600, 1522.891, 1615.659 | 184,006,240; 183,981,684; 184,021,974 | 120.827 MIPS |

Boot is the opposite of Compile. RV64 reaches readiness with 1.7% fewer guest
instructions (`0.9827x` work), but takes 1.5036x as long. Its time per guest
instruction is 1.5301x v86 and throughput is only 0.6535x. Different firmware
and kernel instruction semantics prevent treating MIPS as identical useful
work, but the near-equal counts rule out a 30% compiler-volume explanation.
Boot's remaining gap is genuinely dominated by rewrite T0/runtime throughput,
consistent with the exact CPU profiles.
