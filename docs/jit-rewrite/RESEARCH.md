# State-of-the-Art Research and Design Implications

Research snapshot: 2026-08-06

This document records external design inputs for a WebAssembly-only RV64
dynamic binary translator. The deleted compiler and its historical tuning
documents are intentionally not sources. Primary specifications, runtime
documentation, implementation documentation, and original papers are favored.

## The target is a compiler pipeline, not one JIT

Generated code is compiled twice:

1. RV64 instructions are decoded, optimized, and encoded as WebAssembly.
2. The embedding Wasm engine validates that module and compiles it to the real
   host ISA, potentially through more than one tier.

This makes source-level code quality, Wasm byte size, validation cost, baseline
compiler behavior, top-tier behavior, and the time at which top-tier code
becomes usable all first-class concerns. A transformation that reduces Wasm
instructions but creates an awkward structured CFG can help one engine and hurt
another. Compiler policy therefore cannot be selected from one warmed V8 run.

### Current WebAssembly engine behavior

- V8 initially compiles Wasm with Liftoff and dynamically recompiles hot
  functions with TurboFan. Liftoff deliberately avoids an optimizing IR to
  minimize latency; TurboFan supplies higher peak quality. V8 documents that
  Wasm does not use on-stack replacement, so a long-running invocation remains
  in its original tier even if optimized code becomes available. See V8's
  [compilation pipeline](https://v8.dev/docs/wasm-compilation-pipeline),
  [Liftoff design](https://v8.dev/blog/liftoff), and
  [dynamic tiering](https://v8.dev/blog/wasm-dynamic-tiering).
- SpiderMonkey likewise has a fast Wasm baseline compiler and an optimizing
  Wasm compiler using its optimizing MIR/backend. See Mozilla's
  [SpiderMonkey engine overview](https://firefox-source-docs.mozilla.org/js/).
- Wasmtime exposes Winch as a low-latency baseline compiler and Cranelift as
  its optimizing compiler, but currently selects one compiler for an entire
  module rather than automatically tiering Winch output into Cranelift output.
  See Wasmtime's
  [platform/compiler support](https://docs.wasmtime.dev/stability-platform-support.html)
  and [compiler strategy API](https://docs.wasmtime.dev/api/wasmtime/enum.Strategy.html).
- Wasmer exposes Singlepass, Cranelift, and LLVM as distinct compiler choices.
  Its CLI also provides validation, compilation, and native profiling paths.
  See the [Wasmer CLI documentation](https://docs.wasmer.io/runtime/cli/).

Implications:

- T1 Wasm must be friendly to baseline engines; an expensive optimizing shape
  is not justified by assuming an eventual top tier.
- Long internal guest loops need an experimentally controlled yield/re-entry
  policy. Re-entry can let an engine without OSR start optimized code, but it
  also adds dispatch work. The portable default remains uncapped until paired
  data shows a repeatable win. V8 experiments in this repository found only a
  small top-tier advantage on the current four-module benchmark, while a
  64-Ki-instruction quantum added 3,499 calls without a repeatable wall-time
  improvement.
- Generated bytes and module grouping must be deterministic so identical input
  can be replayed in baseline-only, optimizing-only, and production tiering
  modes. Engine flags are diagnostics, never the headline configuration.
- Module size is a latency/quality control. Tiny modules are cheap to compile
  but lose inter-region optimization; huge modules delay publication and cause
  cold-code compilation. Related hot regions should be batched after profile
  evidence, with a small independently publishable T1 fallback.

## WebAssembly capabilities and constraints

WebAssembly 3.0 includes Memory64. The official feature table reports support
in current Chrome, Firefox, Safari, Node, Wasmtime, and Wasmer releases, while
the Web platform still imposes implementation limits; the WebAssembly project
notes a 16-GiB web limit. See the official
[feature matrix](https://webassembly.org/features/),
[Memory64 specification](https://webassembly.github.io/memory64/core/), and
[Wasm 3.0 announcement](https://webassembly.org/news/2025-09-17-wasm-3.0/).

Memory64 is useful but distinct from emulating a 64-bit ISA. RV64 registers and
arithmetic map directly to Wasm `i64` today; only a guest address space above
4 GiB requires a 64-bit Wasm memory. The implementation should therefore have
two explicit memory capabilities:

- portable `memory32`: 64-bit guest addresses are explicitly range-checked and
  translated into a bounded 32-bit linear memory;
- optional `memory64`: emitted load/store indexes remain `i64`, enabled only
  after feature detection and cross-engine testing.

Core Wasm modules cannot manufacture and publish new executable functions from
bytes by themselves. Decoding, validation, instantiation, imports, and
invocation are separate semantic/embedder phases in the
[WebAssembly specification overview](https://webassembly.github.io/memory64/core/intro/overview.html).
Consequently this design requires a narrow embedder publication service. Hot
execution and helper calls remain Wasm-to-Wasm; JavaScript is not on normal
guest edges.

Wasm tail calls are standardized and implemented by the current major browser
engines and standalone runtimes listed in the official
[feature matrix](https://webassembly.org/features/). They are therefore a
reasonable optional backend primitive, but not a substitute for measurement:
Wasm does not expose Clang's native calling-convention controls, and an
indirect tail-call design may add table, publication, and argument-shuffle
costs. The portable correctness path continues to use an in-module dispatcher.
Direct structured branches inside one shared function and direct tail calls
between functions in one batch should be compared as generated-code variants.

Wasm traps are unsuitable as guest exceptions. Out-of-bounds memory and Wasm
integer division failures abort the generated invocation before the emulator
can publish precise RV64 state. Potentially failing guest operations must use
explicit guards and exact side exits.

### Structured control flow and the Stackifier family

Yuri Iozzelli's Leaning Technologies article
[Solving the structured control flow problem once and for all](https://medium.com/leaningtech/solving-the-structured-control-flow-problem-once-and-for-all-5123117b1ee2)
is directly relevant to a DBT whose input CFG is arbitrary but whose only
target is structured WebAssembly. It contrasts dispatcher/state-variable
reconstruction with Cheerp's Stackifier approach: use CFG ordering, dominance,
loop structure, and nested scopes so ordinary reducible edges become direct
structured branches, reserving exceptional machinery for genuinely difficult
control flow.

The design implication is separate from SSA value stackification. T2 first
forms SCCs, renders reducible cycles with nested Wasm `loop`/`block` scopes,
uses direct depth-indexed branches for known edges, permits only bounded
duplication for small multi-entry SCCs, and localizes a selector dispatcher to
larger irreducible headers. Unknown indirect guest targets remain precise exits.
The implementation follows this family of techniques; it does not claim source
identity with Cheerp's exact dominance-constrained ordering or nesting
heuristics. Directed reducible, irreducible, multi-entry, fuel, and side-exit
tests keep the portable dispatcher backend as a differential control.

## Dynamic binary translation practice

### Current copy/v86 compile policy

The current copy/v86 source was audited at commit
[`2f1346b0e7d88d4cbbbcc05fe15b4e369c3de23f`](https://github.com/copy/v86/commit/2f1346b0e7d88d4cbbbcc05fe15b4e369c3de23f).
Its interpreter measures retired instructions for a physical code page and
collects entry points, using a fixed 200,000-instruction threshold
([policy constants](https://github.com/copy/v86/blob/2f1346b0e7d88d4cbbbcc05fe15b4e369c3de23f/src/rust/jit.rs#L59-L79),
[interpreter accounting](https://github.com/copy/v86/blob/2f1346b0e7d88d4cbbbcc05fe15b4e369c3de23f/src/rust/cpu/cpu.rs#L3155-L3168)).
It generates one 16-bit page or up to three reachable 32-bit pages, maintains
one global in-progress compilation, and publishes through asynchronous
`WebAssembly.instantiate`
([admission](https://github.com/copy/v86/blob/2f1346b0e7d88d4cbbbcc05fe15b4e369c3de23f/src/rust/jit.rs#L2155-L2193),
[browser publication](https://github.com/copy/v86/blob/2f1346b0e7d88d4cbbbcc05fe15b4e369c3de23f/src/cpu.js#L1745-L1827)).

The durable lesson is not its x86 decoder or exact constants. Page heat avoids
per-basic-block compile storms, entry-point discovery bounds the generated
surface, and one asynchronous build prevents compiler work from outrunning the
guest. RV64 additionally needs safe sharing across Sv39 contexts, so the
rewrite keys admission by verified virtual-to-physical page mapping rather than
physical page alone and rechecks that mapping at dispatch/publication.

QEMU's TCG documentation provides several durable DBT invariants:

- translation blocks specialize stable CPU mode/state;
- direct block chaining avoids the central dispatcher for known edges;
- page-local restrictions and linked invalidation records keep chaining sound
  when code mappings change;
- a software TLB gives RAM a checked inline fast path while MMIO and misses call
  helpers;
- guest state can remain unmaterialized inside a block when side metadata can
  reconstruct precise state.

See QEMU's [TCG translator internals](https://qemu.readthedocs.io/en/latest/devel/tcg.html).
The mechanisms cannot be copied literally because Wasm code is immutable after
validation, but the invariants map cleanly to stable table slots, guarded
traces, generation checks, typed TLB capabilities, and side-exit snapshots.

The original [rv8 paper](https://carrv.github.io/2017/papers/clark-rv8-carrv2017.pdf)
argues for a source/target-specific micro-op representation and a hybrid of
direct emission and IR-based translation. That is relevant here: RV64 and Wasm
have unusually direct mappings for integer arithmetic, but high multiply,
division traps, atomics, floating flags, and memory translation require typed
semantic nodes rather than textual opcode substitution.

[Copy-and-Patch Compilation](https://fredrikbk.com/publications/copy-and-patch.pdf)
shows that pre-generated code stencils can provide very low baseline compile
latency with useful code quality. Raw machine-code stencils are unavailable to
a portable Wasm target, but two ideas transfer: preselect compact lowering
recipes by typed operand shape, and keep the T1 pipeline bounded rather than
running an unrestricted optimizer.

Trace JITs demonstrate the value of following measured hot paths, forwarding
state in SSA, and recording exact snapshots at guards. This design adopts those
properties without speculative language types: a region follows direct or
measured edges, and each guard/fault owns an architectural side-exit snapshot.
It deliberately starts with bounded static traces and single-latch loops rather
than an unbounded recorder because guest code, mappings, and interrupt latency
must remain explicit.

Ayush Shukla's 2026 article
[Pushing the limits of RISC-V emulation](https://shuklaayu.sh/blog/riscv-recompiler)
provides a particularly close independent comparison. Its final AOT backend
emits one C function per guest basic block, turns statically known edges into
Clang `musttail` transfers, dispatches unresolved targets through a dense table,
and passes a fixed set of hot guest GPRs with Clang's `preserve_none` calling
convention. This is the native-code counterpart of retaining architectural
state across compiled Wasm region members. Clang documents that
[`preserve_none`](https://clang.llvm.org/docs/AttributeReference.html#preserve-none)
is limited to native x86-64/AArch64, does not alter FP-register handling, and
has an unstable ABI, so the attribute itself is not a portable Wasm mechanism.

The article reinforces two measured experiments for this compiler:

- compare the current eager architectural-register union with bounded live-in
  analysis, lazy entry loads, and a hot-resident/cold-materialized split;
- compare the balanced PC dispatcher on known intra-batch edges with direct
  structured Wasm branches and an optional direct-tail-call backend that keeps
  all target functions in the same module.

Its throughput results are not a performance target for rv64.js. The article
assumes a known static ELF, excludes self-modifying code, uses trusted guarded
linear memory without per-access bounds checks, and benchmarks bare-metal code
without operating-system, syscall, or floating-point behavior. Its larger
results nevertheless support the lifecycle policy here: per-block recompilation
improves regular compute-heavy workloads, while SQLite exposes sensitivity to
indirect-target coverage, short irregular blocks, preparation latency, and code
growth. This argues for captured real-region sweeps rather than selecting a
backend from synthetic steady-state throughput alone.

## RV64, Arm64, and compiler output

RV64 and Arm64 can share the Wasm backend, typed integer/FP operations, memory
capabilities, optimizer, stackifier, publication service, cache, and benchmark
harness. They cannot share most instruction decoding or architectural
semantics. Arm64 has condition flags, conditional/select idioms, richer
addressing, paired accesses, different atomics, and different exception/system
state. RV64 exposes explicit comparisons/branches and a modular extension set.
A future Arm64 implementation should therefore be a second frontend targeting
the same neutral IR, not conditionals scattered through an RV64 decoder.

There is no sound basis for assuming modern compilers produce categorically
inefficient RV64 code. LLVM documents full RV64I support, current application
profiles, scheduling models, and per-core tuning; GCC supports RV64 profiles
and the ratified M/A/F/D/C/B/V and multi-letter extensions. See the
[LLVM RISC-V target guide](https://llvm.org/docs/RISCVUsage.html) and
[GCC RISC-V options](https://gcc.gnu.org/onlinedocs/gcc/RISC-V-Options.html).

The practical risk is an ISA-contract mismatch: a compiler targeting `rv64gc`
will emit A/F/D/C and CSR operations, while an RVA23 binary can additionally
depend on mandatory vector, bit-manipulation, conditional, and other
extensions. The [RVA23 profile](https://docs.riscv.org/reference/rva23/rva23-profiles.html)
makes that expansion concrete. The emulator should publish supported ISA
strings/profiles, test compiler-generated corpora for each one, and prioritize
fallback histograms. For the initial target, `rv64gc` is the sensible complete
contract; RVA23/V should be a separately advertised milestone.

## Selected compiler design

### T0 interpreter

- Correctness oracle and precise fallback for every legal instruction.
- Low-cost PC, edge, indirect-target, unsupported-op, and exit histograms.
- Hotness is based on useful retired work and repeated edges, not wall-clock
  sampling alone.

### T1 bounded region compiler

- Decode a small immutable code snapshot.
- Lift to typed SSA with ordered memory/helper effects.
- Forward architectural registers and keep dirty state in Wasm locals.
- Apply bounded constant folding, dead-value elimination, extension cleanup,
  and target-specific semantic recipes.
- Follow forward direct edges and fallthrough; use exact guards for alternate
  edges. Recognize single-latch backedges as fuel-metered Wasm loops.
- Emit compact functions/modules quickly and publish stable entry slots.

### T2 profile-guided re-formation

- Re-form only demonstrably hot regions; do not layer an expensive generic
  optimizer onto every T1 block.
- Incorporate measured side exits, loop nests, hot direct callees, and a small
  polymorphic indirect-target set.
- Batch related entries into one module/function family so hot edges can remain
  structured Wasm control flow and the second JIT sees useful optimization
  scope.
- Specialize stable architectural context and memory-generation values, with
  guards and versioned cache keys.

### Memory and invalidation

- Flat user memory: explicit unsigned end checks, direct Wasm loads/stores, and
  exact pre-instruction exits.
- Full system: typed fast-TLB entries containing guest tag, host offset,
  permissions, RAM/MMIO class, and generation. A miss/page crossing/MMIO access
  exits or calls a Wasm helper with a complete snapshot.
- Code cache: key by guest PC, architecture context, memory mode, and relevant
  code-page generations. Revalidate asynchronous compilation before publish.
- `FENCE.I`/architectural code-change signals invalidate by code page and unlink
  affected entry slots; never rely on Wasm memory traps for SMC detection.

### Floating point

- Raw bits live in `i64` SSA values, preserving NaN boxing and moves exactly.
- A single Wasm-to-Wasm exact helper ABI handles software operations and ORs
  IEEE/RISC-V flags into forwarded `fcsr` state.
- Direct Wasm FP is enabled only behind a proof. The current proof requires RNE,
  already-sticky NX, finite operands, and result classes that rule out every
  newly observable flag. Unsafe inputs stay on software FP. Dedicated tests
  cover all five modes, NaNs, infinities, signed zero, subnormals, max finite,
  conversions, comparisons, sqrt, min/max, and FMA.

### Atomics and vectors

- User-mode single-thread AMOs can initially lower to one checked ordered
  load/compute/store effect, but LR/SC still needs an explicit reservation
  capability and invalidation rules. Multithreaded guests require shared Wasm
  memory and a proven mapping from the RISC-V memory model to Wasm atomics.
- RVV is not scalar instruction coverage. It needs a vector-state IR, `vl` and
  `vtype` specialization/guards, mask/tail policy, and profitable fixed-width
  Wasm SIMD chunking plus a scalar remainder. It remains a separate milestone.

## Benchmark and validation protocol

### Never hide lifecycle state

Report these independently:

1. guest decode/lift/optimize/emit;
2. byte copy/publication request;
3. Wasm validate/compile;
4. instance construction/import binding;
5. entry publication;
6. first execution and time to break even;
7. production tiering and time to plateau;
8. frozen steady execution;
9. invalidation/retranslation and cache memory.

V8 documents `new WebAssembly.Module()`/`WebAssembly.compile()` as measurements
of baseline compilation in production mode and exposes detailed Wasm tracing
events for baseline and top-tier completion in its
[compilation pipeline documentation](https://v8.dev/docs/wasm-compilation-pipeline).

### Required regimes

- **Cold process:** one workload sample per fresh engine process/profile. Do
  not take best-of-N. Retain every raw sample and report median plus tails.
- **Frozen frontend replay:** capture exact generated bytes, SHA-256 hashes,
  logical entry order, and imports once; compile/instantiate those exact bytes
  in fresh processes and different engines with guest translation removed.
- **Production tiering:** default engine settings, with raw time slices showing
  when execution stabilizes.
- **Diagnostic tiers:** baseline-only and optimizing-only engine modes establish
  sensitivity, but are not product results.
- **Frozen execution:** pre-create all translations, run a correctness check,
  then measure repeated useful guest work without compilation. Reset guest data
  outside the timed interval or use deterministic independent inputs.
- **Invalidation:** mutate/flush a controlled code page and measure detection,
  unlinking, recompilation, and restored steady state.

### Cross-engine matrix

- Chromium/V8 and Node/V8, recorded separately because embedding policy differs.
- Firefox/SpiderMonkey.
- Safari/JavaScriptCore where available.
- Wasmtime with Winch and Cranelift selected separately.
- Wasmer with Singlepass and Cranelift (and LLVM when available).

The current harness provides fresh-process Node samples, phase timings, module
hashes, frozen Node replay, and fresh-process/profile Chrome and Firefox
execution. Chromium is automated through CDP. Firefox 141 removed CDP support,
so current Firefox uses the standardized
[WebDriver BiDi protocol](https://w3c.github.io/webdriver-bidi/) and its
session WebSocket endpoint; Mozilla documents the CDP removal in its
[remote protocol status](https://firefox-source-docs.mozilla.org/remote/cdp/).
This keeps browser setup outside timed intervals while allowing current
SpiderMonkey rather than an obsolete CDP-capable build.

Wasmtime 47 is the standalone delivery gate: it executes every frozen synthetic
backend module with exact-state checks and AOT-compiles the eager real-region
corpus. Earlier Wasmer CLI measurements remain historical toolchain-lifecycle
diagnostics because separate process startup dominates them. JavaScriptCore and
an in-process Winch-versus-Cranelift study would broaden the engine matrix, but
are no longer prerequisites for the completed delivery gate.

### Correctness gates

- full architectural differential: PC, retirement, integer registers, FP bits,
  `fcsr`, traps, and relevant memory;
- directed edge suites for every operation with different Wasm/RV64 failure
  semantics;
- randomized instruction programs crossing tier-up mid-loop;
- generated-module validation at arbitrary code offsets;
- budget/interrupt latency and zero-retirement exit checks;
- memory boundary, page crossing, MMIO, invalidation, atomics, and SMC tests;
- compiler-generated ELF corpus from LLVM and GCC at each advertised ISA
  profile.

## Approaches deliberately not selected

- JavaScript source generation: costly parsing, dynamic-language semantics,
  CSP concerns, and a JS boundary in compiler/runtime policy.
- One Wasm module per guest instruction or per tiny basic block: validation,
  instantiation, table growth, and edge dispatch dominate.
- Wasm traps as guest traps: cannot guarantee precise architectural recovery.
- Unconditional native Wasm FP: cannot reproduce RISC-V rounding modes and
  exception flags.
- A single enormous ahead-of-time module: delays first execution, compiles cold
  code, complicates invalidation, and does not solve dynamic code/mappings.
- Engine-specific flags or best-of-N samples as default-policy evidence.
